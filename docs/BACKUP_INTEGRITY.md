# بکاپ کامل و بررسی یکپارچگی

فرمان backup اکنون منبع SQLite را با اتصال readOnly باز می‌کند و VACUUM INTO سازگار می‌گیرد؛ هیچ seed یا migration روی منبع اجرا نمی‌شود. نبود فایل DB خطاست و دیتابیس تازه ساخته نمی‌شود. مقصد دارای زمان و پسوند تصادفی است تا اجرای هم‌زمان هم روی پوشه قبلی ننویسد.

در آغاز .incomplete در پوشه تازه ساخته می‌شود. نام فایل‌های اصلی/پیش‌نمایش مشتری و رسانه/اصل طرح فروشگاه از snapshot استخراج و از نظر مسیر امن بررسی می‌شوند. hash SHA-256 و طول فایل‌ها از منبع، و سپس از نسخه کپی‌شده، با خواندن جریانی ۶۴ کیلوبایتی تطبیق می‌خورند. نبود حتی یک فایل ارجاع‌شده، خطای کپی یا تفاوت محتوا مانع اعلام موفقیت و ساخت manifest نهایی می‌شود. snapshot و داده ناقص برای بررسی حفظ می‌شوند و پاک‌سازی خودکار ندارند.

فقط پس از کنترل همه ارجاع‌ها manifest نسخه ۲ با اندازه/hash دیتابیس snapshot و فایل‌های ارجاع‌شده نوشته و marker موقت برداشته می‌شود. فایل‌های اضافی معمولی زیر uploads مانند رفتار قبلی کپی می‌شوند، اما فهرست hash فقط داده ارجاع‌شده از snapshot را پوشش می‌دهد. این hash امضای دیجیتال نیست؛ دست‌کاری هم‌زمان manifest و فایل توسط دارنده دسترسی فایل را ثابت نمی‌کند. بکاپ همچنان داده خصوصی دارد و مقصد نیازمند دسترسی محدود و رمزگذاری مستقل است.

مقصد باید از نظر مسیر فیزیکی هم بیرون uploads باشد؛ junction یا symlink نمی‌تواند آن را داخل مبدأ ببرد و کپی بازگشتی بسازد. فایل نمادین و ویژه در مبدأ پذیرفته نمی‌شود. برای مسیر تنظیم‌شده نمادین از مسیر واقعی استفاده کنید.

فرمان مستقل و فقط‌خواندنی npm.cmd run backup:verify -- BACKUP_FOLDER، marker ناقص، قالب manifest، quick_check دیتابیس، حضور جداول orders/uploads، پوشش دقیق ارجاع‌ها و اندازه/hash را بررسی می‌کند. مسیر واقعی پوشه خروجی چاپ‌شده را جایگزین BACKUP_FOLDER کنید. manifest حداکثر ۱۶ MiB پشتیبانی می‌شود. بکاپ قدیمی نسخه ۱ همچنان از نظر ساختار DB و وجود فایل‌ها بررسی می‌شود، اما خروجی صریح می‌گوید hash تاریخی ندارد. این دستور restore یا تغییر فایل انجام نمی‌دهد.

قبل از بازیابی در مسیر جدید، verify را اجرا کنید؛ هیچ بازیابی خودکاری روی داده فعلی اضافه نشده است. هنگام بکاپ همچنان پاک‌سازی فایل را اجرا نکنید. فایل‌های immutable امکان snapshot سپس کپی را می‌دهند؛ تغییر هم‌زمانِ غیرمجاز فایل یا حذف فایل مورد نیاز باعث شکست کنترل می‌شود.

بررسی‌ها فقط در temp: snapshot فقط‌خواندنی و hash همه نوع فایل، CLI verify، خرابی محتوا با حفظ اصل، فایل مفقود و marker ناقص، نبود DB بدون ساخت مقصد، قالب قدیمی، مسیر ناامن manifest/DB و junction واقعی Windows. همچنین تست قبلی بازیابی DB و فایل اصلی پابرجاست. بکاپ، verify یا restore روی داده واقعی اجرا نشده‌اند.
