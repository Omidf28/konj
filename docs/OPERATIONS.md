# استقرار و نگهداری

## وضعیت فعلی
برنامه یک Next.js یکپارچه روی Node.js 24 است. دیتابیس SQLite واقعی، تراکنش BEGIN IMMEDIATE، WAL و busy timeout دارد. برای **یک نمونه برنامه روی یک سرور و دیسک محلی** طراحی شده؛ SQLite روی فایل‌سیستم شبکه‌ای یا چند ماشین اشتراکی اجرا نشود. در صورت نیاز به چند نمونه، لایه repository به PostgreSQL مهاجرت کند.

درگاه، پیامک و شرکت ارسال انتخاب نشده‌اند. رابط‌ها در `src/server/integrations` هستند. برنامه در تولید هیچ پرداخت آزمایشی و هیچ سفارش فروش واقعی ثبت نمی‌کند؛ تا اتصال و تأیید آداپتور واقعی، checkout با 503 متوقف می‌شود. اطلاعات کارت بانکی هیچ‌جا گرفته نمی‌شود. این یک مانع تجاری واقعی است، نه یک پرداخت موفق ساختگی.

## متغیرهای محیط
| نام | کاربرد |
|---|---|
| DATABASE_PATH | مسیر مطلق پایدار دیتابیس؛ پیش‌فرض محلی storage/konj.sqlite |
| UPLOAD_DIR | پوشه خصوصی پایدار فایل‌ها؛ پیش‌فرض storage/uploads |
| APP_ORIGIN | مبدأ دقیق سایت (scheme و host و در صورت نیاز port)؛ در تولید اجباری |
| COOKIE_SECURE | در توسعه HTTPS مقدار 1؛ در تولید Secure به‌اجبار فعال است |
| TRUST_PROXY | فقط وقتی reverse proxy هدر X-Real-IP را از نو می‌نویسد و پورت داخلی عمومی نیست، 1 شود |
| BACKUP_DIR | مقصد خصوصی بکاپ خارج از UPLOAD_DIR |
| TEST_ORIGIN | فقط در fixture خودکار HTTP؛ فرمان test:http:isolated آن را تنظیم می‌کند |

دستورهای ساخت/بازیابی مدیر، بکاپ، انقضای رزرو و cleanup نیز .env* را با loader رسمی Next می‌خوانند. محیط پیش‌فرض CLI توسعه است؛ در سرور تولید پیش از اجرای دستور، NODE_ENV=production را در همان ترمینال تنظیم کنید. متغیرهای صریح فرایند از فایل‌ها بالاترند. مسیرهای نسبی DATABASE_PATH، UPLOAD_DIR و BACKUP_DIR از ریشه پروژه محاسبه می‌شوند، نه پوشه فراخوانی دستور. راهنمای دقیق: docs/CLI_ENVIRONMENT.md.

هیچ مقدار محرمانه در کد یا فایل نمونه قرار نگرفته است. .env، فایل مشتری، دیتابیس و node_modules در Git و context ساخت Docker وارد نمی‌شوند.

## اجرای محلی ویندوز
از ریشه Shop:
```powershell
npm.cmd ci
$env:APP_ORIGIN='http://127.0.0.1:3000'
npm.cmd run dev -- --hostname 127.0.0.1 --port 3000
```
http://127.0.0.1:3000 — پرداخت فقط شبیه‌سازی محلی است و هیچ وجهی جابه‌جا نمی‌کند.

حساب مدیر بدون رمز پیش‌فرض:
```powershell
npm run admin:create -- your_admin_name
```
رمز حداقل ۱۴ کاراکتر دو بار از ورودی تعاملی خوانده می‌شود؛ در آرگومان فرمان قرار نمی‌گیرد. ورودی رمز با ستاره پوشانده می‌شود؛ فقط ترمینال تعاملی پذیرفته می‌شود. رمز با scrypt و salt مستقل ذخیره می‌شود. پنل `/admin` است. این دستور فقط مدیر جدید می‌سازد و حسابی را بازنویسی نمی‌کند.

## اجرای تولید بدون انتشار
```powershell
$env:NODE_ENV='production'
npm.cmd run build
npm.cmd start -- --hostname 127.0.0.1
```
برای تغییرات مدیریتی در تولید، APP_ORIGIN و HTTPS معتبر لازم است. برای بررسی محلی خرید آزمایشی از `npm run dev` استفاده کنید؛ هیچ override برای فعال‌کردن پرداخت آزمایشی در production وجود ندارد.

Dockerfile و compose.yaml آماده‌اند اما Docker روی محیط فعلی موجود نبود و image build آزموده نشده است. compose به loopback میزبان bind می‌شود؛ دامنه نمونه .invalid باید پس از تأیید مالک جایگزین شود. این فایل‌ها به‌خودی‌خود چیزی منتشر نمی‌کنند. volume پایدار برای storage دارد. یک نمونه برنامه اجرا شود. کاربر کانتینر root نیست.

در سرور، reverse proxy با TLS، محدودیت درخواست حدود ۲۳ مگابایت، timeouts معقول و محدودیت نرخ قرار دهید. آدرس فایل مشتری مستقیم سرو نشود. برای مسیرهای `/orders/`، `/api/orders/` و `/api/uploads/` access log شامل URL و query ذخیره نکنید چون توکن پیگیری دسترسی ایجاد می‌کند. لاگ درخواست و Server Function در توسعه خاموش شده؛ خطای برنامه فقط نوع خطا را ثبت می‌کند، نه بدنه مشتری.

## پشتیبان‌گیری
```powershell
$env:BACKUP_DIR='D:\PrivateBackups\Konj'
npm.cmd run backup
```
SQLite با اتصال فقط‌خواندنی و VACUUM INTO snapshot می‌شود، سپس فایل‌های immutable و hash/اندازه فایل‌های ارجاع‌شده بررسی می‌شوند. بکاپ موفق manifest نسخه ۲ دارد؛ پوشه دارای marker با نام .incomplete بکاپ موفق محسوب نمی‌شود. پیش از بازیابی، `npm.cmd run backup:verify -- BACKUP_FOLDER` را با مسیر چاپ‌شده اجرا کنید. جزئیات و محدودیت hash: docs/BACKUP_INTEGRITY.md. هنگام بکاپ پاک‌سازی فایل اجرا نکنید. تمام فایل‌های سفارش همیشه حفظ می‌شوند. پوشه بکاپ حاوی آدرس، تلفن و فایل خصوصی مشتری است؛ دسترسی محدود و رمزگذاری در مقصد مستقل لازم است. انتقال یا خرید فضای بیرونی انجام نشده است.

برای بازیابی ابتدا برنامه را متوقف کنید، از وضعیت فعلی بکاپ بگیرید، فایل دیتابیس بکاپ و پوشه uploads را در **مسیر جدید** کپی کنید، متغیرهای محیط را به آن مسیرها تنظیم کنید و health check و چند سفارش/فایل را بررسی کنید؛ فایل فعلی را حذف یا روی آن کپی نکنید. بکاپ بدون آزمون بازیابی کافی نیست.

## نگهداری
- `/api/health`: سلامت اتصال دیتابیس و وضعیت در دسترس بودن checkout، بدون اطلاعات مشتری.
- `npm run reservations:expire`: رزروهای پرداخت‌نشده بیش از ۳۰ دقیقه را تراکنشی آزاد می‌کند؛ quote و ثبت/پیگیری سفارش هم این کار را انجام می‌دهند.
- `npm run uploads:cleanup`: فقط گزارش dry-run فایل‌های بدون هیچ سفارش و قدیمی‌تر از orphanDays.
- `npm run uploads:cleanup -- --apply`: حذف واقعی فقط با اجرای صریح اپراتور. فایل مرتبط با هر سفارش، حتی لغوشده، حذف نمی‌شود. اکنون هیچ فایل مشتری پاک نشده است.
- محدودیت فایل/سهمیه/نگهداری در تنظیمات مدیر قابل تغییر است؛ quota پیش‌فرض کاربر ۱۰۰ و کل ۱۰۲۴ مگابایت است.
- برای محیط با چند کاربر، TRUST_PROXY را فقط پس از پیکربندی صحیح proxy فعال کنید؛ در حالت پیش‌فرض محدودیت نرخ میان درخواست‌های محلی مشترک و محافظه‌کارانه است.

## اتصال پرداخت واقعی در مرحله عملیاتی
آداپتور انتخاب‌شده باید درخواست پرداخت و تأیید سرور به سرور را با مبلغ، شناسه سفارش، authority و reference بررسی کند. مبلغ مرجع عدد صحیح تومان است؛ تبدیل به ریال فقط با `tomanToRial` انجام می‌شود. تسویه باید در تراکنش با reference یکتا و وضعیت awaiting_payment و مبلغ snapshot انجام شود. callback تکراری نباید اثر دوباره داشته باشد. وضعیت paid از API مدیریت قابل جعل نیست. secrets در محیط سرور قرار بگیرند؛ تا انتخاب درگاه و دریافت دسترسی حساب، آداپتور واقعی پیاده یا فعال نشده است.

## مدل نهایی سه‌بعدی
سه‌بعدی فعلی مدل پارامتریک موقت است؛ آزمایش هندسی فقط فاصله تنه را بررسی می‌کند و آزمون دیداری WebGL/برخورد کامل انجام نشده است. برای جایگزینی، قرارداد BaseModel.model در src/lib/base-model.ts محل URL مدل GLB، anchor جلو/پشت و morph هر سایز را تعریف می‌کند. renderer فعلی procedural-v1 است؛ loader مدل نهایی باید پس از دریافت GLB و ابعاد کالیبره جایگزین شود. هیچ مدل موقت به عنوان تن‌خور نهایی معرفی نشده است.

## ارتقا از نسخه قبلی
پیش از استفاده با داده واقعی، بکاپ بگیرید و برنامه را پس از جایگزینی کد restart کنید. مهاجرت ۴ ستون نسخه محصول/سفارش و تاریخچه را اضافه می‌کند؛ مهاجرت ۵ عرضه‌های مخصوص طرح مشتری را می‌سازد و رکورد قبلی را حذف یا بازنویسی نمی‌کند. عرضه سفارشی اولیه تولید پس از سفارش است؛ برای موجودی خام واقعی، همان عرضه را از مدیریت تنظیم کنید. موجودی محصول آماده چاپ‌شده مستقل می‌ماند. سبد سفارشی قدیمی هنگام quote به عرضه متناظر همان مدل پایه نگاشت می‌شود و مبلغ دوباره تأیید می‌گردد.

در صورت خطای تعارض نسخه، پیش‌نویس مدیر حفظ می‌شود. اطلاعات تازه را دریافت کنید و پیش از ذخیره دوباره، قیمت و موجودی را با نسخه تازه مقایسه کنید؛ موجودی فرم قدیمی را بدون بررسی روی نسخه جدید کپی نکنید.

## محدودیت پردازش فایل
`IMAGE_WORKERS` پیش‌فرض 1 و حداکثر 2 است؛ تغییر نیازمند restart است. درخواست اضافه هنگام اشغال ظرفیت با 429 و Retry-After پاسخ می‌گیرد. سقف دریافت هر درخواست ۳۰ ثانیه است؛ reverse proxy باید محدودیت بایت و زمان سازگار داشته باشد. سهمیه کل فایل‌ها اکنون شامل اصل و تصویر بهینه فروشگاه هم می‌شود. مهاجرت ۶ اندازه فایل‌های قدیمی را از UPLOAD_DIR می‌خواند؛ مسیر قبلی را پیش از ارتقا تنظیم کنید. اطلاعات کامل در docs/RESILIENCE.md است.

## تمرین بازیابی بدون داده واقعی

`npm run test:recovery:isolated` دو دیتابیس/پوشه تازه موقت می‌سازد، از بکاپ رسمی بازیابی و برنامه را از نسخه بازیابی‌شده اجرا و HTTP/فایل/موجودی را مقایسه می‌کند. مسیر واقعی نمی‌پذیرد و fixtureها را برای بازبینی نگه می‌دارد. نتیجه و محدودیت اندازه‌گیری: [R12_ACCEPTANCE.md](R12_ACCEPTANCE.md).

پذیرش production و restart ایزوله پس از build: `npm run test:recovery:isolated -- --production`. این حالت به داده واقعی وصل نمی‌شود و checkout تولید را باز نمی‌کند؛ جزئیات و شکاف‌های TLS/Docker/میزبان: [R13_ACCEPTANCE.md](R13_ACCEPTANCE.md).

## رسیدگی به سفارش‌های نخست

1. سفارش را در پنل مدیریت با شناسه خودش باز کنید. پیش از شروع تولید، وضعیت و رویداد پرداخت را بررسی کنید. اگر نتیجه پرداخت نامشخص است، سفارش را متوقف نگه دارید و مبلغ و مرجع را از طریق درگاه منتخب تطبیق دهید.
2. در برگه تولید، SKU، رنگ، اندازه، تعداد و سمت چاپ را با سفارش تطبیق دهید. اصل فایل را از لینک همان سمت دریافت کنید. اگر اصل فایل یا مشخصات لازم موجود نیست، قبل از تولید پیگیری کنید.
3. پس از کنترل کیفیت، برگه بسته‌بندی را برای شمارش اقلام و تطبیق نشانی باز کنید. وقتی مرسوله تحویل روش ارسال تأییدشده شد، کد رهگیری را ثبت کنید و وضعیت ارسال را در همان سفارش بررسی کنید.
4. اگر ثبت وضعیت یا کد رهگیری پاسخ روشنی نداد، اطلاعات تازه سفارش را دریافت و با پیش‌نویس مقایسه کنید. در صورت لغو سفارش پرداخت‌شده، رسیدگی مالی و ثبت مرجع بازپرداخت بر اساس سیاست مصوب جداگانه پیگیری می‌شود.
5. قبل از شروع پذیرش واقعی و پس از نخستین سفارش‌ها، سلامت سرویس، موجودی، سهمیه فایل و بکاپ قابل بازیابی را بررسی کنید. در محیط آزمایشی، پاسخ checkout در مسیر /api/health هنگام غیرفعال بودن سفارش آزمایشی disabled است.

پذیرش این روند با روش ارسال، درگاه و سیاست واقعی در R15/R17 ثبت می‌شود. مسیر فعلی برای تمرین با سفارش آزمایشی آماده است.
